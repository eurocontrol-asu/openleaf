# Contributing to OpenLeaf

## Development Setup

```bash
git clone https://github.com/eurocontrol-asu/openleaf.git
cd openleaf
uv sync --all-groups
uv run pre-commit install
```

## Making Changes

1. Create a branch: `git checkout -b feat/my-change`
2. Make changes in the relevant package under `packages/`
3. Run tests: `make test-all`
4. Run lint + type-check: `make check`
5. Commit with conventional commits: `feat(pkg): description`
6. Open a pull request

## Local Testing with BADA Data

Tests that exercise BADA3 and BADA4 models depend on proprietary data files that are not redistributed with this repository. Two environment variables tell the test suite where to find them:

```bash
export OPENLEAF_BADA3_PATH=/path/to/bada/3.16
export OPENLEAF_BADA4_PATH=/path/to/bada/4.2.1
```

If these variables are unset, BADA-dependent tests **skip cleanly** — they do not fail. You can run the full suite without BADA access and still get a green build:

```bash
make test-all   # BADA tests skip, OpenAP / Poll-Schumann / physics / numpy tests still run
```

CI checks out a private `bada-data` repository and exports both variables, so the full suite always runs on `main` and pull requests.

For Phase-4 characterization tests (golden numerical fixtures pinning model outputs), the fixtures themselves are committed to git under `packages/openleaf-performance/tests/characterization/fixtures/`. This means contributors **without** BADA data can still verify that a refactor preserves model behaviour — they just can't regenerate the fixtures. The regenerator lives at `tests/characterization/_regenerate_fixtures.py` and is maintainer-only (leading underscore excludes it from pytest collection).

## Adding a Package

1. Create `packages/my-pkg/` with `pyproject.toml`, `src/`, `tests/`
2. UV auto-discovers members via the `packages/*` glob in the root `pyproject.toml`
3. Run `uv sync --all-groups` to update the lockfile

## Release Process

Releases are tag-driven and the changelog is generated automatically. **Do not hand-edit `CHANGELOG.md`** — it is regenerated by [`git-cliff`](https://git-cliff.org/) from conventional commit messages at tag time. To produce a release:

1. Ensure your commits follow conventional-commit format (`feat:`, `fix:`, `refactor:`, etc.) — this is what `git-cliff` parses.
2. Tag the release: `git tag -a v0.2.0 -m "v0.2.0"`
3. Push the tag: `git push origin v0.2.0`
4. The release workflow (`.github/workflows/release.yml`) regenerates `CHANGELOG.md` and publishes the release.

Conventional commit groups defined in `cliff.toml` map to changelog sections (`feat → Added`, `fix → Fixed`, `refactor → Changed`, etc.). Anything that doesn't match a known prefix is filtered out, so non-conventional commits silently disappear from the changelog — please follow the convention.
